# Compiler Unification & Cross-Language Verification Plan

This document outlines the implementation plan to unify the Java Fluent API so that it strictly emits `ImpScheme` S-Expressions, bringing it into parity with the rest of the ecosystem. It also details the creation of a cross-language C++ vs Java testing harness.

## User Review Required
> [!IMPORTANT]
> **C++ Shared Library Path**: To load the C++ engine via FFM for the side-by-side verification harness, we will need to load `libimpulse_graph.dylib` (or `.so`). We'll assume the C++ library will be built in `../impulse-graph-core/impulse-cpp/build/`. Please confirm if there is a preferred path or dynamic loading strategy for the C++ shared library during maven test execution.

## Proposed Changes

### Phase 1: Compiler Debugging & Optimization Toggles
Before tearing out the old compiler, we will instrument the new pipeline to ensure complete observability.

#### [MODIFY] `impulse-compiler/src/main/java/org/impulsegraph/compiler/cel/CelCompiler.java`
- Add `java.util.logging.Logger` gated by a `DEBUG_MODE` static boolean.
- Dump the S-Expression AST after parsing and after every subsequent AST pass (e.g., `RegisterAllocationPass`).
- Dump the final `ImpAsm` assembly text generated by the `ImpOpsBytecodeEmitter`.

#### [MODIFY] `impulse-vm/src/main/java/org/impulsegraph/vm/ImpulseMethodHandleCompiler.java`
- Introduce a system property flag: `-Dimpulse.compiler.disable_jit=true`.
- When toggled, the compiler will bypass the MethodHandle JIT combinators (unrolling) and force the emission of standard, unoptimized `impOps` scalar bytecodes. This ensures the generated `.impb` bytecode is identical and portable across the C++ and Java engines for debugging.

---

### Phase 2: C++ vs Java Cross-Engine Test Harness
We need a rigorous way to guarantee that identical bytecode produces identical results in both the Java FFM engine and the native C++ engine.

#### [NEW] `impulse-vm/src/test/java/org/impulsegraph/vm/CrossEngineVerificationTest.java`
- Create a parameterized test harness.
- **Java Engine Execution**: Run the bytecode payload through `ImpulseVmInterpreter`.
- **C++ Engine Execution**: Use Java 25 FFM `SymbolLookup.libraryLookup(...)` to dynamically load the `impulse-graph-core` C++ shared library. Expose a simple `extern "C"` FFI binding (e.g., `impulse_execute_bytecode(snapshot_ptr, bytecode_ptr, length)`) using `Linker.nativeLinker().downcallHandle()`.
- **Assertion**: Compare the final returned scalars, row cursors, or bitset outputs of both engines to ensure 100% parity.

---

### Phase 3: The `ImpScheme` Unification Refactor
With the safety nets and testing harness in place, we will gut the hardcoded compiler loop.

#### [MODIFY] `impulse-api/src/main/java/org/impulsegraph/api/ImpulseQueryBuilder.java`
- Remove the `StepNode` POJO entirely.
- Refactor the fluent builder methods (`.walkEdge()`, `.filter()`, etc.) to incrementally construct an `ScmProgram` (a tree of `ScmNode` objects) instead of appending to a list.

#### [DELETE] `impulse-vm/src/main/java/org/impulsegraph/vm/ImpulseQueryCompiler.java`
- The custom `compile(List<StepNode>)` logic will be deleted.
- The `execute()` method in the builder will now pass the constructed `ScmProgram` directly to `ImpOpsBytecodeEmitter.emit()`, yielding the standardized `impOps` bytecode payload.

## Verification Plan
### Automated Tests
- Run `mvn clean test -pl impulse-vm` to ensure the Fluent API still perfectly evaluates the existing 50 tests using the new S-Expression pipeline.
- Run `CrossEngineVerificationTest` to validate that the C++ kernel yields identical traversal frontiers as the Java engine for identical S-Expression inputs.
